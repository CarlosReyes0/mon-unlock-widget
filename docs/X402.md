# x402 payments, unlock logging, and report freshness

Bankr and other agent wallets pay **USDC on Base** (`eip155:8453`) for
`POST /api/x402/publish` and `GET /api/x402/articles/{slug}`. Human readers
still unlock USDC on Monad. This page covers the payment log, the stats view,
and the unpaid freshness probe. It does not change who gets charged.

## Repeat unlocks charge every time

An x402 unlock does **not** grant an entitlement. Paying once does not write
`unlocks` or `fiat_unlocks`, and the next call without a reader session or
`fiat_session` is another HTTP 402. Settling that challenge charges again.

These still skip the x402 charge:

- `X-Reader-Session` from `POST /api/reader/session` when that reader already
  unlocked the article (on-chain or Stripe).
- `fiat_session` for a succeeded card unlock.

A bare `reader=0x…` query param is not an entitlement. Subscribe-only articles
still return 403.

`x402_payments` is an audit log. It is not consulted when deciding access.

## Table `x402_payments`

Service role only. Row level security is enabled and there are no policies for
`anon` or `authenticated`.

| Column | Notes |
| --- | --- |
| `id` | uuid primary key, `gen_random_uuid()` |
| `kind` | `publish` or `unlock` |
| `article_id` | nullable bigint foreign key to `articles.id` (`on delete set null`). Publish can be paid before a row exists; the slug is resolved to `articles.id` when the row is already there. |
| `payer` | EVM `authorization.from` on the decoded `X-PAYMENT` / `PAYMENT-SIGNATURE` payload. Solana uses an explicit payer field on that payload when one is present. Otherwise the facilitator settle response `payer` field. |
| `amount_atomic` | USDC atomic units (6 decimals) that this charge required |
| `network` | settle network, else the payment payload network, else `base` |
| `asset` | Base USDC contract |
| `tx` | transaction hash from the settle response |
| `created_at` | timestamptz, default `now()` |

Indexes: `(article_id, kind)` and `payer`.

Both paid handlers (`handleX402Publish`, `handleX402Unlock`) insert one row
after the paid work succeeds. The insert is fire-and-forget: it is not
awaited, and any lookup or insert failure is `console.error` only. A logging
failure cannot change the 200 response. Dev-bypass requests are not logged
because no payment settled.

Migration: `supabase/migrations/0017_x402_payments_report_checks.sql`.

## View `x402_article_stats`

One row per `article_id` (payments with a null article are omitted):

| Column | Definition |
| --- | --- |
| `unique_payers` | `count(distinct payer)` |
| `total_unlocks` | `count(*)` where `kind = 'unlock'` |
| `amount` | `sum(amount_atomic)` across publish and unlock rows for that article |
| `last_paid_at` | `max(created_at)` |

The view is `security_invoker` and `security_barrier`. `SELECT` is revoked from
`PUBLIC`, `anon`, and `authenticated`, and granted to `service_role` only.
The underlying table has no public policies, so a public API key cannot read it.

## Table `report_checks`

Service role only, same RLS posture as `x402_payments`.

| Column | Notes |
| --- | --- |
| `endpoint` | primary key and upsert target. One of `POST /api/x402/publish`, `GET /api/x402/articles/{slug}`, `POST /api/agents/publish/validate`. |
| `article_id` | text slug for the article probe; null for the other two checks. This is the public slug, not `articles.id`. |
| `last_tested` | timestamptz |
| `status` | `live_402_challenge`, `live_200_free`, or `failing` |
| `details` | jsonb: `httpStatus`, `acceptsNetworks`, `latencyMs`, plus method and url |

Classification of each **unpaid** response:

- `live_402_challenge` — HTTP 402 and a valid x402 challenge (`x402Version` 1 or 2 with a non-empty `accepts` entry that has a network or scheme, in the JSON body or the `PAYMENT-REQUIRED` header).
- `live_200_free` — HTTP 200.
- `failing` — anything else, including a 402 that is not a valid challenge, a network error, or a missing probe slug.

## Unpaid probe

`POST /api/x402/report/probe`

Protected the same way as follow notify: header `x-x402-report-probe-secret`
must match the server env var **`X402_REPORT_PROBE_SECRET`**. An empty or
missing secret never authenticates.

The handler then calls, with no payment headers and no facilitator request:

1. `POST /api/x402/publish` with `{}` (invalid body, so a stray payment header
   would 400 before charge).
2. `GET /api/x402/articles/{slug}` where `{slug}` is **`X402_REPORT_PROBE_SLUG`**.
   If that env var is unset, the article check is stored as `failing` and no
   article URL is requested.
3. `POST /api/agents/publish/validate` with a harmless validate body (title,
   slug `x402-report-probe`, teaser, body, and a non-publishing publisher
   address). Validate does not create an article.

The only write is the `report_checks` upsert. The probe does not pay, does not
publish, and does not insert `x402_payments`.

### Schedule

`0017_x402_payments_report_checks.sql` schedules pg_cron job
`open-paywall-x402-report-probe` every 15 minutes (`*/15 * * * *`). The job
`POST`s `https://openpaywall.app/api/x402/report/probe` via pg_net, sending
`x-x402-report-probe-secret` from Vault name **`x402_report_probe_secret`**.

Create the vault secret with the same value as `X402_REPORT_PROBE_SECRET`
before the job can succeed. Do not put the secret in the migration.

```sql
select vault.create_secret(
  '<paste X402_REPORT_PROBE_SECRET — do not commit it>',
  'x402_report_probe_secret',
  'Open Paywall x402 unpaid report probe'
);
```

### Env vars

| Name | Where | Purpose |
| --- | --- | --- |
| `X402_REPORT_PROBE_SECRET` | app server | Shared secret for `POST /api/x402/report/probe`. Header `x-x402-report-probe-secret`. |
| `X402_REPORT_PROBE_SLUG` | app server | Slug passed to `GET /api/x402/articles/{slug}` during the probe. |
| `x402_report_probe_secret` | Supabase Vault | Same value as `X402_REPORT_PROBE_SECRET`, read by the cron job. Not an app env var. |

Existing x402 and Supabase settings still apply (`X402_PAY_TO` or
`MPP_TEMPO_RECIPIENT`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`). If x402
is not configured, the unpaid publish and unlock probes classify as `failing`
(503), which is the truthful freshness result.
